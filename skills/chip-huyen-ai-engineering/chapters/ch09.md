## 先测瓶颈与目标

推理服务接收、路由、可能预处理请求，再由推理服务器在目标硬件执行模型。优化分模型、硬件和服务三层；质量、延迟、吞吐、成本可能相互牵制。先用实际输入/输出长度、并发与流量曲线测量，再决定技术。

自回归 LLM 的 **prefill** 并行处理输入，通常更受计算量制约；**decode** 逐个生成输出 token，通常更受权重/KV 在存储层间搬运的带宽制约。算力瓶颈与带宽瓶颈可由算术强度和 roofline 分析判断；“memory-bound”有时指带宽，有时指容量不足，排障时要讲清。上下文、输出长度、batch 与硬件会改变瓶颈，不能把“prefill 一律算力、decode 一律带宽”当所有场景的定律。

在线 API 优先响应时间；批量 API 可放宽完成时间以争取成本和吞吐。章节里各服务商折扣属于当时例子，不能作当前报价。流式返回改善用户看到第一个字的时间，但未完整审查的内容会先显示；高风险场景要设计发布前校验。这里的“批量 API”仍是请求到达后处理，与传统 ML 预先算完有限预测的“batch inference”不同。

## 指标与成本核算

**延迟**是请求至完整回答时间；**TTFT** 是首个可见 token 的等待，**TPOT/ITL** 是后续 token 生成间隔。书中粗略公式为 TTFT 加生成 token 数乘 TPOT，实践中需明确首 token 是否已含在 TTFT。代理内部规划或工具调用可能延迟用户可见首字，因此区分模型首 token 与用户首个可见内容。看 p50/p90/p95/p99，并按输入长度、输出长度、并发和错误分层，而非仅报均值。

**吞吐**可分别计输入/输出 tokens/s，也可计完成请求/s 或 /min。比较不同 tokenizer 的 tokens/s 会失真，业务成本/完成请求更有意义。**goodput** 只统计满足 TTFT、TPOT 等服务目标的完成请求。GPU“忙碌时间利用率”不是有效工作量；**MFU** 近似实际模型计算量对硬件峰值算力之比，**MBU** 近似实际带宽使用对可用带宽之比。两者受模型、batch 和测法影响，最终以质量约束下的成本与延迟判定。

根据每小时硬件成本、prefill 吞吐和 decode 吞吐分别估算每请求成本，再加路由、存储、缓存、空闲、网络与运维。书中 7B FP16 × 100 token/s 的算术应为约 **1400 GB/s**，不是 OCR 所示 700 GB/s；以 2 TB/s 为分母才得 70% MBU。这是可见 OCR/算术不一致，不能照抄数字。

## 硬件与模型压缩

CPU 擅长通用与顺序控制，GPU/TPU 等加速器擅长并行矩阵运算。选型至少核对目标精度下的有效 FLOP/s、可用显存、内存带宽、互联、功耗和价格，并在目标 workload 上实测。峰值算力可能基于稀疏或特定形状，不能直接代替应用表现。CPU 内存、GPU HBM、片上 SRAM 的容量/带宽差异解释了为何数据移动和内核布局重要。

模型压缩可用量化、蒸馏、剪枝。量化降低权重精度通常最易试，但需回归质量；蒸馏训练较小学生模型，要区分训练/授权成本；剪枝移除节点或让部分权重为零，实际提速依赖硬件和内核能否利用稀疏性，不能只看“零参数占比”。模型层优化可能改变行为，所以每版须回归业务与安全评价。

## 生成与注意力优化

**推测解码**让快速草稿模型提议若干 token，由目标模型并行验证并接受最长合格前缀；速度受草稿成本、接受率、目标模型闲置计算能力和文本域影响。**reference-based decoding** 从输入中找可复用片段作为草稿，适合输出与上下文大量重叠的任务。**并行解码**尝试多头或迭代预测未来 token，需验证一致性，实现较复杂。书中加速倍数均是特定实验，不应当作通用承诺。

**KV cache** 缓存历史 token 的 key/value，避免逐 token 重算，容量随序列长度、batch、层数、维度与数值字节线性增加。对于未压缩的多头形式，可用 2×batch×序列长×层数×维度×每值字节估算；MQA/GQA 等结构需换对应 KV 头数。书中 “attention 随长度指数增长” 与章末注释中的 **O(n²)** 冲突；应以二次复杂度表述标准全注意力。长上下文可考虑局部/全局窗口、跨层共享、MQA/GQA、PagedAttention、KV 量化/压缩/选择，但架构改动和缓存优化的适用阶段不同。

**FlashAttention** 通过更适配硬件的数据移动与融合内核加快注意力。内核常用向量化、并行化、分块和算子融合；编译器将高层模型操作降到硬件可执行内核。不同 GPU 架构可能需要不同实现；加速后仍需测输出质量、精度与成本。

## 服务调度

- **静态 batching** 等固定请求数，低流量时等待长；**动态 batching** 加最大等待窗；**连续 batching** 在某请求完成后立即交付并补进新请求，适合输出长度差异大的 LLM。原文“batching reduces throughput”明显与上下文冲突，应理解为提升吞吐、可能增加单请求等待。
- **prefill/decode 分离**把不同资源曲线的阶段放不同实例，可能改善 goodput；需计中间状态传输和机器间带宽，实例配比按实际输入/输出长及 TTFT/TPOT 目标调整。
- **prompt/prefix caching** 复用重复系统提示、长文档或对话前缀，减少重复 prefill；收益取决于命中率、缓存保留、容量与收费。章节的价格和折扣不能用作现价。
- **副本并行**增加实例处理并发；**张量并行**把同一算子分到多设备，可放下大模型但有通信成本；**流水线并行**按层/阶段拆模型，单请求可能增加延迟；上下文/序列并行服务长输入。部署时以显存、互联与 SLO 约束求解模型和副本的放置。

**诊断顺序**：测质量、p95 TTFT/TPOT、goodput、输入/输出分布与总成本 → 判定算力、带宽、容量、队列或网络瓶颈 → 选择最小改动的缓存/批量/副本/量化等候选 → A/B 回归质量与负载峰值 → 记录回滚条件。
