## 先定义评估标准

作者提出 **evaluation-driven development**：建设应用前定义如何判断它是否有价值。评估要连接业务目标，避免系统已经上线却无法证明结果。先列四组准则：领域能力、生成能力、指令遵循、成本与时延。合同摘要例如同时要懂法律文本、忠实且连贯、符合字数和格式、在预算与响应时间内完成。每个维度分硬门槛和理想水平，能否妥协由业务决定。

领域能力可用代码执行、SQL 执行准确率及效率、领域问答或分类测试。多选题容易自动评估，但对格式与提示敏感；“选出正确答案”和“独立生成好答案”不是同一能力。代码能运行还需检查效率、可维护性。生成质量可看流畅、连贯、相关、忠实及具体任务要求；强模型的流畅文字并不保证事实可靠。事实核查分 **local**（是否被给定文档、政策或数据支持）与 **global**（是否符合外部可验证知识）。后一种先要确定可信来源；未找到证据不等于已证明相反命题。

事实核查可让裁判核对、把长答拆成原子陈述后检索验证，或用 textual entailment/NLI 分成蕴含、矛盾、中立。中立表示材料不足，不能自动记作真实。SelfCheckGPT 用多次生成间的不一致作为幻觉线索，但成本高且一致不等于正确。SAFE 采用拆句、补足指代、搜索、逐条判断的流程。测试集应包含冷门知识、并不存在的人物/事件等易幻觉情形。TruthfulQA、RealToxicityPrompts、BOLD 等是书中示例；任何一个公共基准只覆盖其定义的切面。

安全评价需按应用定义不当语言、危险建议、仇恨、暴力、刻板印象、政治或宗教偏向等类别，可用专用分类器、通用裁判及人工抽检。指令遵循要与领域知识区分：懂情感分类但输出了不允许的标签，是遵循失败；不会写越南诗可能是知识或遵循问题。IFEval 用可程序验证的关键词、长度、JSON 等约束；INFOBench 把内容、风格等复杂指令拆成可问的子标准。角色扮演还需分别测表达风格、角色知识与“不该知道”的信息，例如游戏 NPC 泄露剧情。公共指令集无法代替自己的真实任务。

成本与延迟要用应用真实请求测 TTFT、每 token 时间、整次请求 P90 等，并区分“必须达到”和“最好达到”。输出 token 数、采样、提示长度与服务负载均会影响延迟。API 以用量收费，自托管有计算、工程和运维费用；规模变动后应重算，而非只比标价。书中虚构的阈值表及 GPU 容量是示例，不是建议直接使用的预算。

## 模型选择流程

先筛 **hard attributes**：许可证、数据边界、隐私、部署位置、模型规模等无法或不愿改变的条件。再用公共基准和排行榜缩小候选，随后在自有评估管线中做真实任务实验，最后上线持续监测。准确率、毒性和提示效果等可能是 **soft attributes**，但改善空间需实验而非凭想象；对第三方 API，延迟或功能限制可能属于硬条件。

“自托管还是模型 API”按七轴评估：数据隐私、训练数据来历与版权、性能、服务功能、总成本、控制权、端侧部署。书中把“open source”宽泛用于公开权重模型，同时说明严格意义的开放还涉及训练数据与许可证。下载到权重不等于可商用，也不等于允许用输出训练其他模型；逐个查当前许可证及上游输出使用条款。闭源 API 与开放权重托管 API 都可能有不同供应商、服务特性和性能，同名模型换提供商也要回归测试。自托管可获得权重、logprobs 与优化控制，但需负责弹性、工具调用、结构化输出、护栏、监测与故障恢复。API 可加快开始，却依赖服务条款、速率、版本和可用性。当前法律、隐私和版权判断要咨询最新权威资料，不能凭此书定论。

## 公共基准的用途和局限

公共基准有助于排除明显不合格模型，不能直接判定本业务最佳模型。排行榜选哪些基准、如何加权，决定了它奖励什么能力；不同榜单内容可能大幅不同。简单平均把难度、业务重要性和相关性均视为相同，还可能重复计入高度相关的基准。基准会饱和，且公开题目可能进入预训练、微调或提示优化。数据污染可用训练集与测试集的 n-gram 重叠检查；低困惑度只能提示潜在污染，不能证明。若能接触训练数据，应报告脏样本比例及清洁子集成绩；否则优先用新鲜的私有任务样本。排行榜和社区投票的任务分布也可能与企业 RAG、客服或代码工作流不一致。

## 建立评估管线

**步骤 1：逐层评价。** 同时测端到端任务、每轮回复及中间组件。简历 PDF 中“当前雇主”提取错误可能出在 OCR，也可能出在实体抽取；分别测才能定位。多轮助手既要看单轮质量，也要看能否完成任务、花了几轮。

**步骤 2：写评分指南。** 说明该做什么、什么输入越界、遇到越界如何回应。把“好”拆为相关、事实一致、安全、帮助程度等适用准则，给每个准则明确量尺和各档样例。先由人类测试是否能一致理解规则，再用于 AI 裁判或标注。把评价分数映射到业务目标和最低可用门槛；例如客服自动解决率与事实一致率的关系必须用本业务数据估计，不能搬用书中示意比例。留意只追求停留时长等指标可能伤害用户利益。

**步骤 3：选择方法与数据。** 用可执行测试优先验证功能，必要时组合分类器、参考答案、AI 裁判、专家抽检。可让便宜方法覆盖全部流量，昂贵方法抽样深检；抽样率与漏检风险一起记录。logprobs 若可用，可帮助分类置信分析，但概率高并不保证结论真实。采用真实生产样本，标注端到端、各组件和不同评价准则。至少建立代表生产分布的集、高风险/常错集、拼写错误与越界集，并按用户、输入长度、主题、渠道等切片。只看总分可能发生 Simpson 悖论。

样本量与目标要检验：bootstrap 重采样观察结果波动，差异越小通常要越多样本。书中“30% 差约 10 个、10% 差约 100 个、3% 差约 1000 个、1% 差约 10000 个”是粗略经验表，不能代替本数据的显著性或功效分析。最后反过来评价评估器：好回答是否得高分、评价指标能否预测业务效果、重复运行与换样本后方差、指标是否冗余、评估本身的成本与延迟。迭代评价标准时版本化数据、评分表、提示、采样及裁判，否则历史分数不能直接比较。

## 交付格式（本 Skill 整理）

- **业务目标与门槛**：任务完成、风险上限、P90 延迟、单次成本。
- **筛选表**：候选模型、硬条件、公共基准线索、自有样本结果。
- **评估数据**：生产代表集、难例集、越界集、各切片和标注来源。
- **评估方法**：组件测试、任务测试、人工与 AI 裁判的分工及版本。
- **上线结论**：达标/未达标、误差范围、主要失败模式、复测日期。

**自测**：为何公共榜单第一不保证客服场景最优？local 和 global factual consistency 的证据范围有何不同？如何把一次简历提取错误定位到 OCR 或实体抽取？评价标准改版后，为什么不能直接比较前后均分？
